# 네이버 블로그 운영 비서 개발 명세

## 배경

현재 프로젝트는 네이버 검색 표면별 순위 조회와 관심 키워드 추적에 초점이 맞춰져 있다. 다음 단계의 제품 방향은 단순한 랭크 확인 도구가 아니라, 네이버 블로그를 운영하는 1인이 매일 사용할 수 있는 개인 운영 비서다.

핵심 전환:

```text
순위 확인
-> 발행 전 글 개선
-> 발행 후 순위 피드백
-> 기존 글 DB 기반 리라이트/신규 소재 추천
```

## 참고한 유료 솔루션 패턴

국내 네이버 블로그 도구와 해외 SEO/유튜브 도구에서 공통적으로 확인한 유료 가치 지점은 아래와 같다.

1. 키워드 검색량, 경쟁도, 트렌드, 난이도 분석
2. 현재 순위와 순위 이력 추적
3. 경쟁 콘텐츠의 제목, 태그, 구조, 누락 주제 분석
4. 발행 전 콘텐츠 점수와 개선 가이드
5. 기존 콘텐츠 가져오기와 리라이트 제안
6. 최적 발행 시간, 알림, 리포트
7. 경쟁자/경쟁 글 변화 감지

이 프로젝트에서는 외부 유료 데이터에 의존하지 않고, 네이버 검색 결과에서 관찰 가능한 정보와 내 블로그 DB를 우선 활용한다.

## 제품 목표

가족가 글을 쓰기 전과 후에 아래 질문에 바로 답하게 만든다.

1. 지금 이 키워드는 내가 공략할 만한가?
2. 이 글은 올리기 전에 무엇을 보강해야 하나?
3. 내 기존 글과 키워드가 겹치지는 않나?
4. 발행 후 순위가 왜 오르거나 떨어졌나?
5. 오늘 새 글을 써야 하나, 기존 글을 고쳐야 하나?

## MVP 1: 발행 전 본문 분석 코치

### Phase 1 구현 범위

2026-04-20 Phase 1에서는 외부 검색 결과나 유료 데이터 없이, 사용자가 입력한 키워드/제목/본문만으로 결정적인 1차 점검을 제공한다. `독자 기대 정보 누락`은 실제 상위 글 문장이나 구조를 복제하지 않고, 키워드 의도와 독자가 자주 기대하는 정보 요소를 기준으로 빠진 항목을 추정한다. 실제 상위글 비교와 누락 주제 후보 연결은 MVP 3에서 확장한다.

수용 기준:

1. `core/content_analyzer.py`는 `webapp`이나 `bot`에 의존하지 않는 순수 분석 모듈이다.
2. 입력값은 `keyword`, `title`, `body`이며 셋 중 하나라도 비어 있으면 호출 계층에서 400 오류를 반환한다.
3. 결과는 총점, 내부 프록시 점수 문구, 항목별 점수/제안, 우선 수정 항목, 제목 후보, 소제목 후보, 위험 경고를 포함한다.
4. 모든 점수 표현은 네이버 공식 점수가 아니라 내부 프록시 점수로 표기한다.
5. 위험 요소는 키워드 도배, 과장/단정 표현, 중복 문장, 지나치게 짧은 본문, 민감 주제 단정 표현을 우선 탐지한다.
6. UI는 현재 모바일 웹앱 안에서 간단한 입력 폼과 결과 영역으로 제공한다.

구현 결과:

1. `core/content_analyzer.py`가 `ContentAnalysisRequest`, `ContentAnalysisResult`, `ContentCheck`와 `analyze_content()`를 제공한다.
2. `POST /api/content-analysis`는 인증을 요구하고, 빈 `keyword`/`title`/`body`를 400 오류로 거부한다.
3. 응답에는 `score`, `summary`, `score_label`, `intent`, `checks`, `priority_actions`, `title_suggestions`, `heading_suggestions`, `risk_warnings`, `missing_topics`, `input_warnings`, `benchmark_notes`, `content_stats`가 포함된다.
4. 웹앱 상단 메뉴의 `발행 전 분석` 화면에서 키워드, 제목, 본문을 입력하고 결과를 확인한다. 첫 화면은 랭크 확인 기능을 우선한다.
5. 테스트는 `tests/test_content_analyzer.py`와 `tests/test_webapp.py`에 추가했다.

2026-04-20 후속 UX/분석 보완:

1. 첫 화면은 다시 랭크 확인 중심으로 유지하고, 발행 전 본문 분석은 상단 메뉴에서 이동하는 보조 화면으로 분리한다.
2. 네이버 블로그 편집기에서 이미지를 포함한 본문을 복사하면 textarea에는 이미지가 들어오지 않고 빈 줄이 많이 들어올 수 있으므로, 분석 전 과도한 빈 줄을 정리하고 사용자에게 입력 정리 안내를 보여준다.
3. 결과에는 내부 프록시 점수와 별도로 `benchmark_notes`를 제공한다. 이 항목은 네이버 공식 순위 요소가 아니라, 네이버 서치어드바이저의 공개 SEO/스팸 가이드와 블로그 운영 실무에서 널리 쓰이는 점검 관점(명확한 제목, 독자 의도, 경험 근거, 이미지 설명, 중복/도배 회피)을 참고한 내부 벤치마크 메모다.
4. 상위글이나 유명 블로그의 문장, 구성, 표현을 베끼는 방식은 금지하고, 독자가 기대하는 정보 요소를 놓치지 않게 하는 체크리스트로만 사용한다.
5. 발행 전 분석 화면에는 작성자가 최신 네이버 공식 가이드를 직접 확인할 수 있도록 네이버 SEO 기본 가이드와 웹 콘텐츠 스팸사례 링크를 노출한다.

2026-04-23 분석 고도화:

1. 응답에는 `photo_checklist`, `differentiation_guidance`를 추가한다.
2. `photo_checklist`는 키워드 의도, 본문 통계, 누락 항목을 바탕으로 필요한 사진/캡처 장면을 제안한다.
3. `differentiation_guidance`는 상위글 반복 항목, 기존 내 글 중복, 내부 링크 후보를 묶어 이번 글에서 앞세워야 할 차별점 방향을 제안한다.
4. 이 제안은 상위글 복제 지시가 아니라, 기본 정보와 실제 경험을 어떻게 분리해 보여줄지에 대한 운영 가이드다.

2026-04-23 분석 결과 정리:

1. 발행 전 분석 화면은 작성에 바로 쓰는 정보만 우선 노출한다.
2. `상위글 제목/요약 기반 누락 후보`는 본문 누락 항목과 직접 맞닿고, 상위글 제목/요약에서 2회 이상 반복된 후보만 보여준다.
3. `내 글 내부 링크 후보`는 키워드나 목표 주제가 실제로 가까운 글만 제한적으로 보여준다.
4. `본문 통계`는 사진/지도처럼 행동으로 이어지는 수치만 노출하고, 단순 줄 수 같은 저신호 수치는 숨긴다.
5. `공개 가이드/실무 벤치마크`는 내부 참고 메모로 유지하되 기본 화면에서는 노출하지 않는다.

### 2026-04-23 외부 AI 보강 분석

규칙 기반 분석은 계속 제품의 기본값으로 유지하되, 외부 AI를 붙일 수 있으면 더 짧고 실무적인 보강 코멘트를 추가한다. 이 보강층은 규칙 기반 결과를 대체하지 않고, 제목/첫 문단/차별화 포인트를 다시 정리해 주는 보조 계층이다.

수용 기준:

1. 외부 AI는 설정이 없으면 비활성이고, 제품은 기존 규칙 기반 분석만으로 계속 동작한다.
2. 기본 제공자 설정은 `Groq`와 `qwen/qwen3-32b`를 기준으로 둔다.
3. 설정은 `AI_PROVIDER`, `AI_API_KEY`, `AI_MODEL`, `AI_BASE_URL` 환경변수로 제어한다.
4. 응답에는 `ai_feedback`가 추가될 수 있으며, `summary`, `priority_actions`, `title_suggestions`, `opening_paragraph`, `differentiation_point`를 포함한다.
5. AI 호출 실패는 전체 분석 실패로 번지지 않고, `ai_feedback=null`로만 처리한다.

## MVP 2: 기존 포스팅 DB화

### 목적

DB화는 저장 자체가 목적이 아니다. 작성 전 코치와 발행 후 피드백의 근거 데이터를 만드는 것이 목적이다.

### 2026-04-20 Phase 2 보강 구현 범위

현재 앱에는 `내 글` 저장과 글별 키워드 순위 확인 흐름이 이미 있다. 이번 단계는 이 흐름을 유지하면서 Phase 2 명세에 필요한 메타데이터와 표준 API를 보강한다.

수용 기준:

1. 기존 `/api/my-posts`와 UI는 계속 동작한다.
2. 명세 표준에 맞춘 `/api/posts` 계열 별칭을 추가한다.
3. 저장 글은 `blog_id`, `post_id`, `category`, `published_at`, `content_summary`, `content_hash`를 포함한다.

5. 목표 키워드는 `post_keywords.keyword_type = target` 기본값을 가진다.
6. 글 수정, 글별 키워드 추가, 글별 키워드 삭제가 API에서 가능하다.
7. UI는 카테고리, 발행일, 글 요약을 입력/표시한다.

구현 결과:

### 2026-04-20 Phase 2.5 내 블로그 공개 글 가져오기

## MVP 3: 상위글 비교 분석기

### 2026-04-20 Phase 3 구현 범위

이번 단계는 `기준별 상위글 보기`에서 이미 수집한 `GET /api/blogs` 결과를 발행 전 본문 분석에 연결한다. 경쟁글 본문을 복사하거나 우회 수집하지 않고, 검색 결과에서 관찰 가능한 제목과 요약만 사용한다.

수용 기준:

1. `POST /api/content-analysis`는 선택 입력 `reference_posts`를 받을 수 있다.
2. `reference_posts` 항목은 `title`, `summary`, `url`만 사용하며 본문 HTML이나 경쟁글 원문 수집 필드는 받지 않는다.
3. `core/content_analyzer.py`는 상위글 제목/요약에서 반복되는 토픽을 추출하고, 기존 `missing_topics`와 겹치는 항목을 우선 후보로 표시한다.
4. 응답에는 `serp_missing_topic_candidates`가 포함된다. 이 값은 상위글을 베끼기 위한 자료가 아니라 독자 기대 정보 확인용 후보임을 문구로 명시한다.
5. 웹앱은 `기준별 상위글 보기` 결과를 재사용해 발행 전 분석 요청에 `reference_posts`를 첨부한다. 같은 키워드 결과가 없으면 분석 전에 기존 `GET /api/blogs`를 호출해 동일한 결과 구조를 재사용한다.
6. UI 섹션 제목은 `상위글 제목/요약 기반 누락 후보`로 표시한다.

구현 결과:

1. `ReferencePost` 입력 모델과 `SerpMissingTopicCandidate` 응답 모델을 추가했다.
2. 반복 토픽은 의도별 체크리스트 사전과 제목/요약 토큰 빈도를 함께 사용해 추출한다.
3. 기존 `missing_topics`와 겹치는 후보를 먼저 정렬하고, 본문에 이미 있는 토픽은 일반 반복 후보에서 제외한다.
4. UI는 같은 키워드의 최근 `GET /api/blogs` 결과가 있으면 그대로 쓰고, 없으면 분석 전 기존 엔드포인트를 호출해 `reference_posts`를 만든다.
5. `상위글 제목/요약 기반 누락 후보` 섹션에는 후보 토픽, 반복 글 수, 본문 누락 항목과의 일치 여부, 베끼기 방지 안내를 보여준다.

### 2026-04-21 실발행 쇼핑 글 피드백 보정

## MVP 3.6: 네이버 데이터랩 인기 키워드

### 2026-04-21 구현 범위

네이버 실시간 검색어는 폐지됐지만, 데이터랩 쇼핑인사이트는 분야별 인기 검색어를 공개 화면에서 제공한다. 또한 Signal은 별도 서비스로 실시간 검색어 API를 사용하고 있다. BMS는 글감 탐색용으로 이 정보를 별도 `인기 키워드` 탭에 보여준다.

수용 기준:

1. 출처는 `네이버 데이터랩 > 쇼핑인사이트 > 분야별 인기 검색어`로 명시한다.
2. 실시간 검색어 또는 검색량 절댓값으로 표현하지 않는다.
3. `순위`, `인기 키워드`, `발행 전 분석`, `내 글` 탭으로 분리한다.
4. 기본 카테고리는 `패션의류`이고, `패션잡화`, `화장품/미용`도 바로 바꿔 볼 수 있게 한다.
5. 키워드를 누르면 기존 순위 검색 입력에 들어가고 바로 순위 확인을 실행한다.
6. 네이버 공식 API 문서상 분야별 Top 10 키워드를 바로 주는 API는 확인되지 않았으므로, MVP는 공개 데이터랩 화면을 파싱한다.
7. Signal 실시간 검색어는 `https://api.signal.bz/news/realtime` 응답을 사용하되, 네이버 공식 데이터가 아니라 외부 서비스로 명시한다.
8. 파싱 또는 외부 API 실패 시 화면에는 실패 안내를 보여주고 기존 순위 기능은 계속 동작한다.
9. 주간/월간과 API 키 기반 클릭 추이 조회는 후속으로 남긴다.

API:

```text
GET /api/datalab/shopping-keywords?category=50000000
GET /api/signal/realtime-keywords
```

응답:

```json
{
  "source": "naver_datalab_shopping_insight",
  "source_label": "네이버 데이터랩 쇼핑인사이트 분야별 인기 검색어",
  "category": {"id": "50000000", "name": "패션의류"},
  "time_unit": "date",
  "period": "2026.04.18.(토)",
  "items": [
    {"rank": 1, "keyword": "원피스", "url": "https://datalab.naver.com/shoppingInsight/sKeyword.naver?keyword=..."}
  ],
  "fetched_at": "..."
}
```

Today 헤더 보정:

1. 헤더 우측 Today 미니 영역은 최대 3개 관심 키워드를 가로로 보여준다.
2. 순위 표기는 축약 라벨을 사용해 두 줄 줄바꿈을 줄인다.
3. 변화 배지는 미니 영역에서 숨기고, 자세한 변화는 관심 키워드/오늘의 새 소식 영역에서 본다.
4. 순위 탭 첫 화면은 `오늘 요약`, `지금 검색`, `관심 키워드`가 먼저 보이게 하고, `오늘의 새 소식`, `최근 검색`, `최근 저장 이력`은 접어서 둔다.

### 2026-04-22 로컬 운영 안정화

작은 로컬 PC 또는 소형 VM에서는 Playwright 작업이 겹치면 메모리와 응답 안정성이 빠르게 나빠진다. 웹앱은 사용자가 여러 버튼을 연속으로 눌러도 브라우저 작업을 직렬화하거나 즉시 거절해야 한다.

보정 기준:

1. Playwright를 쓰는 웹앱 API인 `/api/rank`, `/api/blogs`, `/api/posts/import-target-blog`, `/api/my-posts/{id}/check`는 한 번에 하나만 실행한다.
2. 다른 브라우저 작업이 이미 진행 중이면 `409`와 사용자용 안내 문구를 반환한다.
3. 브라우저 자동화 실패나 공개 글 가져오기 실패는 raw 예외를 노출하지 않고, 사용자용 한국어 메시지로 `502`를 반환한다.
4. 입력 검증과 인증 실패는 기존처럼 `400`/`401`을 유지한다.
